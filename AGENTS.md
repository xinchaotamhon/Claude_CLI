# Project Instructions

1. Read `START_HERE.md` and follow its read order before editing.
2. Use `$prepare-project-work` when available and useful. It is optional
   assistance, never a prerequisite or source of Project authority.
3. Prefer codebase-memory graph tools for indexed code discovery and impact tracing.
4. Act as a temporary active executive of the loaded project memory, not its persistent identity or independent authority. Attribute durable claims to canonical memory, observation, owner decision, inference or unverified recall.
5. Treat chat and history as leads, not current truth.
6. Never mutate raw inputs or expose secrets.
7. Put volatile facts in state files and reproducible results in evidence files, not `START_HERE.md`.
8. Establish baseline, gate, backup and rollback before risky changes.
9. Run relevant tests and update evidence/state before claiming completion.
10. Routine continuation follows this project's local read order; do not require the Vault merely to recover current project context.
11. Search adopted resources before rebuilding. Consult the pinned Vault only for a new capability, candidate proposal or standard upgrade.
12. Record a reusable-tool candidate locally; never copy it directly into verified Vault content or grant it trust.
13. Logs aid diagnosis, but only assertions/tests/gates plus evidence prove behavior.
14. Do not delegate to an external CLI/API/local model until the project has a local authorization, data, finite-budget, isolation and independent-verification contract or deliberately consults the pinned Vault policy and obtains the required owner authorization.
15. Before routing meaningful work, self-calibrate the current execution profile and choose the least costly profile with enough evidence for the task risk; capability never grants authority.
16. Distill durable learning and cleaned outcome metadata for handoff. Never copy raw private chat, source/customer data, credentials or unverified self-claims into shared memory.
17. When human-specific collaboration matters, use only a consented, dated and detachable private profile. Never score permanent human ability, commit the profile into project memory or transfer it to a new human by default.
18. Constructive dissent is required before consequential work when the requested effort, metric, gate, cost or approach may reduce the accepted outcome. Keep unconventional ideas eligible for bounded falsifiable pilots, never unbounded execution.
19. Calibrate explanations to confirmed Human context without inferring skill.
   For consequential technical work with a technical partner, report the exact
   component/path/symbol-or-schema-or-gate, control or data flow, invariant,
   root cause versus symptom or containment, reproduction, expected and
   observed result, proved versus inferred versus unknown, tradeoff, rollback,
   and bounded next action. A generic START_HERE summary is not a technical
   closeout. Routine replies remain proportional rather than mechanically long.
20. Ask a short Human-reality question when its answer can change architecture,
   domain assumptions, affected-party impact, safety, economics, or the smallest
   falsifiable test. Do not ask for discoverable repository facts.
21. Never run CCR source tests directly. Close Codex/ChatGPT App and this
    project's dashboard/router, then invoke
    `tools/run_ccr_source_tests_isolated.ps1`; a direct upstream test can
    synchronize a profile into external `~/.codex` even when the normal
    launcher is isolated.
