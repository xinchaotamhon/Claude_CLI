- Privacy: sanitized design/verification patterns only; no credential, account

## Why this proposal exists

`D:\mydata\my-project\CLOVER\START_HERE.md` and its routed governance files
were inspected read-only. They contributed the useful discipline of separating
stable routing, volatile state, evidence and candidate resources. A bounded
resource search did not find a direct verified card for dynamic model-catalog
promotion, hidden Windows bootstrap lifecycle or recoverable account removal.
The mismatch is useful field evidence, not permission to add unreviewed facts.

## Candidate 1 — Catalog discovery is not launch capability

When an external provider returns a dynamic model catalog, preserve the full
sanitized catalog for observation but expose a launch route only when all three
links are proved:

1. catalog entry exists for the authenticated account;
2. the exact pinned adapter/runtime registry supports the model;
3. a bounded local readiness gate exposes the model on the intended isolated
   endpoint.

Unknown or future models stay visible but non-routable. This prevents a fresh
provider label from becoming an unsupported or misrouted capability claim.

Suggested evidence fields: provider family, sanitized catalog model ID, pinned
adapter version/hash, registry source/hash, local endpoint scope, gate result,
provider-request-consumed boolean, observed timestamp and rollback.

## Candidate 2 — One action, hidden success, visible failure

For a Windows one-click launcher, hide only the bootstrap process after it has
a durable diagnostic path. The owner action should return immediately on
successful detached startup, while a genuine failure writes a project-local
ignored log and opens that log visibly. A hidden console must not imply hidden
failure or background mutation outside the project root.

Suggested gate: one double-click creates zero bootstrap consoles, at most one
requested interactive terminal, one verified loopback service and one bounded
diagnostic artifact on failure.

## Candidate 3 — Destructive-looking controls remain recoverable

Account/session deletion should identify the exact owned target, refuse an
active target when needed, stop only its verified process, move state to
project-local trash with a recovery manifest and remove only the corresponding
UI route/card. Code rollback must not require credential deletion.

This pattern is especially relevant where users need to manage expiring API or
subscription accounts without asking an AI to edit secret files.

## Candidate 4 — Resource-discovery mismatch as evidence

The real project query crossed UI accessibility, Windows process lifecycle and
dynamic provider capability. Generic discovery returned no directly adoptable
verified resource. CLOVER could retain this sanitized NO_MATCH case to improve
future query terms and candidate routing, without treating this project as an
authority or copying its implementation.

## Acceptance gate for any later CLOVER contribution

- Owner explicitly approves the sanitized contribution.
- The receiving repository chooses its canonical resource/candidate location.
- Claims cite this project's tracked evidence, not chat history.
- No raw runtime/auth/quota/transcript data crosses repositories.
- Candidate status remains unverified until independently reproduced.
